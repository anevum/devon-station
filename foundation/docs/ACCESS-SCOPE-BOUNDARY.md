# Cloudflare Access scope boundary: offline review

This module maps a subject returned by a trusted, independently configured provider verifier to an explicit server-owned scope grant. It is not a JWT verifier, session manager, HTTP middleware or production integration. Caller-provided emails and roles are not authorization. Revalidate provider authentication and authorization at each protected operation, including after lock waits as appropriate. Provider identities and keys used in tests are synthetic.

Recovery PR #1 `worker/access.mjs` remains a separately reviewed component, not imported or copied into this branch. The original offline review discovered that the recovered verifier accepted malformed signed `nbf` claims. That defect was addressed in the separate recovery draft at commit [`5c93f23`](https://github.com/anevum/devon-station/commit/5c93f2315cafff16d63668938293e526ef5d9140). The `access-interop` CI job checks out that exact recovery commit alongside this branch, creates throwaway RSA test keys, and checks JWT validation plus server-owned scope mapping end to end. No production key, credential, account or live service is involved. The pinned commit is intentionally not auto-updated; changes to the recovered verifier require explicit review and renewed tests. Locally, check out the two draft branches into separate directories and run `RECOVERED_ACCESS_MODULE=../../recovered/worker/access.mjs node --test interop/access-scope-interop.mjs` from `scoped/foundation`.

This test does not establish live Cloudflare Access policy, real identity formats, token revocation, tenant isolation in a deployed system, or release readiness.

Cloudflare distinguishes Access-protected direct Workers using the runtime-provided `ctx.access` identity from application JWT validation at other origins. See https://developers.cloudflare.com/workers/configuration/cloudflare-access/ and https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/ . In either case the deployment must independently verify the actual trust boundary, audience, issuer, lifecycle and source-specific identity format. No claim from a client header or unsigned payload should establish a principal.

Scope grants in this experiment are immutable copies supplied by trusted server configuration. A current grant must be resolved for each protected operation in any production implementation; this prototype has no live grant reload, revocation, encrypted persistence, recovery, production authentication or external operations. Do not use with real data.
